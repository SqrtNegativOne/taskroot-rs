# Taskroot-rs Architecture & Guide for AI Agents

**CRITICAL**: When you modify the architecture, tech stack, or file structure of this project, you MUST update this `AGENTS.md` file to reflect the new state. Always verify if the information here is outdated and update any old information if needed.

*Note: Domain-specific rules are located in `src/AGENTS.md` (for Svelte) and `src-tauri/AGENTS.md` (for Rust).*

## Working With the User
- **Never screenshot the desktop or a running app to inspect the UI.** Do not launch the app just to capture it either. The user runs it themselves and will send a screenshot or describe the screen when asked — ask them.
- Prefer non-visual introspection for your own checks: ask the user, read logs, or reason from the code. Screen capture is for image files the user hands you, not for verification.

Taskroot is a desktop task management app focusing on planning, executing, and resting. It is built as a Svelte 5 application running on a native Tauri v2 Rust backend.

Planning docs live at the repository root: [CLEANUP-BACKLOG.md](CLEANUP-BACKLOG.md) is the in-place cleanup list (current layout) and [RESTRUCTURE-PLAN.md](RESTRUCTURE-PLAN.md) is the target layout. They are backlogs, not a description of the current tree; this file describes the code as it is.

## Tech Stack
- **Package Manager**: Bun (`bun`). Used for package management and running frontend scripts.
- **Frontend Framework**: Svelte 5 with SvelteKit configured for SPA (Single Page Application) mode (`ssr = false` in `src/routes/+layout.ts`, `adapter-static` with an `index.html` fallback). Uses Svelte runes for reactivity.
- **Build Tool**: Vite (via SvelteKit), fixed dev port 1420 (`vite.config.js`).
- **Desktop Wrapper**: Tauri v2 (Rust backend, configured in `src-tauri/tauri.conf.json`).
- **Language**: TypeScript (`.ts`, `.svelte`) on the frontend, Rust (`.rs`) on the backend.
- **Date Math**: `date-fns` (narrow named imports) supplies week/day arithmetic in `src/lib/time.ts`; `ymd` stays hand-written so `format` and its locale data are not pulled in.
- **Styling**: Vanilla CSS (`src/app.css`) with extensive use of CSS variables for theming.
- **Backend / Storage**: One CalDAV server (local Radicale) is the source of truth. At startup, on connect, and when the user presses Refresh, the Rust backend loads every collection into an in-memory `Store` (`src-tauri/src/store/`); there is no background sync and no on-disk cache of calendar data. Edits merge into the stored raw `.ics` and `PUT` immediately. App settings and per-component UI state live in `settings.json` / `ui-state.json`. There is no SQLite database, offline queue or Google client any more.
- **Type Sharing**: `ts-rs` generates `src/lib/bindings/*.generated.ts` from Rust structs; `cargo nextest run` is the regeneration trigger (see Key Concepts).
- **Testing**: 
  - **Frontend E2E**: Playwright (`playwright.config.ts`, specs in `tests/e2e/`, run via `bun run test`; the config boots `bun run dev` on port 1420 with chromium).
  - **Frontend Unit**: Vitest with jsdom (`bun run test:unit`). Coverage is collected via `@vitest/coverage-v8` (`bun run coverage:frontend`).
  - **Backend**: Rust unit tests (`cargo nextest run` in `src-tauri`, including CalDAV XML-parser fixtures, ICS round-trip invariants and `AppError` shape checks). `src-tauri/examples/e2e_caldav.rs` is the live Radicale check. Coverage is collected via `cargo-llvm-cov` (`bun run coverage:backend`, requires `cargo install cargo-llvm-cov`).
- **Linters**: ESLint (strictTypeChecked; `**/*.generated.ts` is exempt from `array-type` and `consistent-type-definitions` in `eslint.config.js`) and Rust `clippy` (`lib.rs` warns on pedantic/nursery and denies `unwrap`/`expect`). Source and config files are linted; only generated/vendor directories are ignored. Svelte's three pointer-UI a11y warnings (`a11y_autofocus`, `a11y_click_events_have_key_events`, `a11y_no_static_element_interactions`) are filtered once in `svelte.config.js`; do not add per-node `svelte-ignore` comments. CI (`.github/workflows/ci.yml`) runs `bun run check` + `bun run lint` and `cargo clippy --all-targets -- -D warnings` + `cargo nextest run`. **CRITICAL: You must run `bun run check` (for frontend) and `cargo clippy` (for backend) after EVERY change to ensure code quality and avoid regressions.**

## Project Structure
- `src/`: SvelteKit frontend codebase.
  - `src/routes/`: SvelteKit routing (`+layout.svelte`, `+page.svelte`). The single SPA branches on the Tauri window label (`main`, `launcher`, `minitracker`, `sidebar`, `effect`) inside `+layout.svelte`. `src/routes/effect/` is the transparent, click-through full-screen phase-transition overlay.
  - `src/routes/settings/`: Settings screen split into `schema.ts` (typed schema consuming the generated `AppSettings` type) and `SettingRow.svelte`.
  - `src/lib/`: Shared logic and Svelte runes:
    - `store.svelte.ts`: Primary store. Mutations return `neverthrow` `Result`s, await the backend command, then emit `store-updated` so live queries re-fetch. Wrap user-triggered mutations in `store.mutate(operation, action)` so failures surface as error notifications; `store.error` is reserved for fatal load/bootstrap failures. `init()` is idempotent (one cached bootstrap promise) and reads `get_settings` once on mount.
    - `safeInvoke.svelte.ts`: `safeInvoke` (`ResultAsync` wrapper over `invoke`) and the `useTauriQuery` rune (stale-guard via request IDs, optional `debounceMs`).
    - `errors.ts`: Typed `BackendErrorCode`/`AppError` glue mirroring the Rust `AppError` contract (`normalizeAppError`, `describeAppError`).
    - `toast.ts`: `notifyError(message)` wraps `svelte-sonner`'s `toast.custom` with the click-to-copy `CopyableToast` and `duration: Infinity`; the `<Toaster>` is mounted in `+layout.svelte` in every window except `effect`. Use it for transient operation failures instead of `store.error`.
    - `ipcEvents.ts`: TypeScript mirrors of the backend event-name constants in `src-tauri/src/ipc_events.rs`.
    - `eventColor.ts`: Shared event-accent presentation (`eventColorVars`) emitting the `--ev-color`/`--ev-bg` custom properties both the date grid and day timeline consume, so their colors cannot diverge.
    - `time.ts`: Local-date/time helpers (`ymd`, `parseLocalYmd`, `formatHhMm`, `startOfWeek`, `startOfMonth`, `getWeekNumber`, `isoWeeksInYear`, `isoWeekYear`, `addDays`, `dayDiff`, `sameDay`, `MS_PER_MINUTE`), delegating week/day arithmetic to narrow `date-fns` imports. Never use `toISOString()` for day bucketing (it shifts to UTC).
    - `queries.ts`: Named builders for backend query arguments (`eventInstances(range, filters, query)`, `allEvents()`, `activeCalendars()`), so command names and argument shapes have one home. Keep the builders thin; `commands/tests.rs` still guards the wire contract.
    - `useNow.svelte.ts`: Shared reactive `now` primitive (one interval, cleaned up automatically); use it instead of ad-hoc rAF loops.
    - `persisted.svelte.ts`: `persistState` rune + `persistedKeys` that hydrate per-component UI state (filters, sorts, view modes, pane sizes, collapsible sections) from `ui-state.json` via `get_ui_state` and debounce-save changes via `set_ui_state`, flushing pending writes on destroy.
    - `asyncState.svelte.ts`: Shared backend-hydration primitives composed by `persistState` and `useTauriQuery`: `createStaleGuard` (drop out-of-order responses), `createDebouncer` (coalesce delayed callbacks with flush/cancel), `createDebouncedWriter` (write specialization built on the debouncer), and `hydrateOnce` (read-once-on-mount). Not a framework; compose them and keep state local.
    - `routes.ts`: Centralized route-path constants.
    - `domain.ts`: Centralized domain barrel re-exporting generated bindings from `src/lib/bindings/` and domain models/events/timing/filters (modularized in `src/lib/domain/models.ts`, `events.ts`, `timing.ts`, `filters.ts`). `events.ts` also owns `buildNewEvent`, the single constructor for new-event drafts shared by the plan screen and sidebar; `timing.ts` provides the only render-path day-overlap helper (`instanceOccursOnDay`).
  - `src/lib/bindings/`: Generated TypeScript bindings (`.generated.ts`) for Rust data structures (generated via `ts-rs` by running `cargo nextest run` in `src-tauri`). Never hand-edit.
  - `src/screens/`: Major UI views. `plan/` (with `snapping.ts` as the one snapping/duration-clamp home, `day-timeline/`, including `hooks/pointerGesture.svelte.ts` — a window-pointer gesture registry with `pointercancel` and teardown safety — and `date-grid/`, plus `hooks/eventDrag.svelte.ts`, `hooks/taskDrag.svelte.ts`, `date-grid/dropTarget.ts`, `date-grid/dropPayload.ts`, and `date-grid/spanLayout.ts` for pointer drag-and-drop of grid instances onto other grid days or the timeline and for dragging a task onto the grid to create a linked event, with multi-day all-day events rendered as per-week spanning bars) and `do/` (with `stopwatch/`, whose `engine.svelte.ts` consumes the generated `StopwatchState`, defaults to the flowtime/flomodoro clock — work counts up, taking a break counts down one fifth of the work done, then waits for the user to restart work — and still offers the plain counter style; it includes the timed pause, plays the transition WAVs, and triggers the screen-effect overlay). `sidebar/state.svelte.ts` persists the sidebar's tab position/notes/visibility under `ui.sidebar.*` in `ui-state.json`.
  - `src/components/`: Reusable UI components. `ComingSoon.svelte` consolidates the seven stub route pages; `inspector-pane/` is split into `InspectorPane`, `state.svelte.ts` (queries, selected item, mutations and recurring-delete scope prompt), `InspectorTaskFields`/`InspectorEventFields`, and `format.ts`; `tasklist/ListManagerModal.svelte` creates/renames/recolours/deletes CalDAV lists from the task pane.
  - `src/test/`: Shared test utilities (`tauriMock.ts`, the process-wide Tauri IPC mock; `setup.ts`, which installs the Tauri runtime globals that the externalized `@tauri-apps/api/event` reads; and `factories.ts` with `makeEvent`/`makeInstance` defaults for domain fixtures). See `src/AGENTS.md` for the testing conventions.
- `src-tauri/`: Tauri Rust backend.
  - `src-tauri/src/lib.rs`: Lints, module wiring, app-data resolution (`app_data_dir`: `TASKROOT_DATA_DIR` override, plus a debug-build fallback to `<exe dir>/dev-data` when the real app-data directory is not writable — see Development Environment Notes), managed `StoreState`, startup load and `run()`. IPC commands live in `commands/`, not here.
  - `src-tauri/src/load.rs`: The one-shot loader. `load_all` re-reads `account.json`, refreshes the collection list, and replaces the in-memory resources with `ops::full_load`; it runs at startup, after `connect_account`, and from the manual `refresh_data` command (`commands/refresh.rs`). It emits `store-updated` when done. There is no poller, no change hook and no delta/token logic.
  - `src-tauri/src/commands/`: IPC command handlers split by domain (`tasks.rs`, `events.rs`, `calendars.rs`, `plan.rs`, `schema.rs`, `settings.rs`, `window.rs`, `refresh.rs`, `stopwatch.rs`) plus `session.rs` (shared `client_for`/`store_state`/`app_calendar` plumbing). Every handler is a thin wrapper over the store/CalDAV layer. Tauri requires owned `AppHandle`/argument values, so the module carries one documented `needless_pass_by_value` allow instead of per-handler ones; `commands/tests.rs` pins the `generate_handler!` table against the frontend call sites (see `src-tauri/AGENTS.md` → Command Testing).
  - `src-tauri/src/caldav/`: CalDAV protocol layer. `transport.rs` owns the shared `reqwest::Client` and status mapping; `xml.rs` holds request bodies and `roxmltree` parsers; `discovery.rs` resolves principal → calendar-home → collections; `account.rs` persists `account.json` and the keychain password; `client.rs` adds `fetch_resources` (one `calendar-query`) / `fetch_hrefs` / `put_resource` / `delete_resource` / `mkcalendar` / `proppatch`; `calendars.rs` owns the collection lifecycle (create/rename/recolour/delete, mirroring `account.json` and `store.calendars`); `connect.rs` builds the account/client pair from the stored account and keychain password (shared by the app and the CLI; `TASKROOT_CALDAV_PASSWORD` overrides it); the IPC account/list commands live in `commands/calendars.rs`; `model.rs` defines `CalendarInfo`/`CalendarComponent`.
  - `src-tauri/src/store/`: The CalDAV-backed in-memory store. `model.rs` holds `Store`/`Resource`; `ops/` is split by aggregate (`load.rs` for `full_load`, `events.rs` and `tasks.rs` for the scoped writes, `mod.rs` for shared helpers and re-exports so `ops::delete_event` call sites do not move; immediate `PUT`/`DELETE`, one re-fetch/retry on `412`); `query.rs` is the in-memory filter/sort/search; `persist.rs` reads/writes `settings.json` and `ui-state.json`; `state.rs` is the managed `tokio::sync::Mutex` handle.
  - `src-tauri/src/error.rs`: `AppError` enum (`thiserror`) returned by ALL IPC commands; serialized as `{code, message}`.
  - `src-tauri/src/ipc_events.rs`: Centralized event-name constants (`STOPWATCH_UPDATED`, `STORE_UPDATED`, `DEEP_LINK`, `SCREEN_EFFECT`).
  - `src-tauri/src/domain/`: Core data structures split into `ids.rs` (the id newtypes plus the small identity enums), `event.rs` (`AppEvent` with `is_recurring()`, `AppCalendar`, `EventScope`), and `task.rs` (`AppTask`), with `mod.rs` re-exporting so imports do not change; `sigil.rs` for sigil parsing, `filters.rs` for filter columns/types, `projection.rs` for expanding stored events into `EventInstance`s, and `timing/` (recurrence helpers in `timing/recurrence.rs`) plus `event_timing.rs` — the **single normalization boundary** (`EventTiming`, `EventInstance`, `EventTiming::from_event`) that turns raw calendar strings into tagged all-day/timed timing. Nothing outside this module may parse `AppEvent::start_time`/`end_time`.
  - `src-tauri/src/ics/`: CalDAV resource ↔ DTO conversion. `read.rs` maps a whole `.ics` body (with `icalendar`) to `Vec<AppEvent>`/`Vec<AppTask>`; `write.rs` is the line-preserving editor that merges an edit into the fetched bytes (only Taskroot-owned property lines change; `VTIMEZONE`, `ATTENDEE`, `SEQUENCE`, `LOCATION`, unknown `X-*` survive verbatim, and a `VALARM` is only rewritten when the task's reminder list changed) and `lines.rs` holds that editor's folding/component-spanning core, including nested components (`VALARM` inside `VTODO`, `STANDARD` inside `VTIMEZONE`) whose lines belong to the nested component only. `create_*_resource` builds a brand-new resource with `icalendar`'s builder. Never serialize a DTO to a resource (I1), a resource is a set of components sharing a UID (I2), and unknown components never round-trip through `icalendar` (I3). Fixtures under `ics/fixtures/` are real Radicale resources.
  - `src-tauri/src/stopwatch.rs`: Stopwatch state and clock helpers (`StopwatchState`, `StopwatchManager`, `with_locked_state`, `current_epoch_millis`). The IPC wrappers live in `commands/stopwatch.rs`.
  - `src-tauri/src/settings/`: Settings backend, split into `mod.rs` (`AppSettings` struct with `#[derive(TS)]` and `#[derive(SettingsMeta)]` field-adjacent metadata) and `metadata.rs` (`SettingMeta`/`SettingOption`, `SETTING_SECTIONS`, and `build_settings_schema`, with tests in `metadata/tests.rs`); the settings/UI-state IPC commands live in `commands/settings.rs`. `get_settings_schema` is generated from the field attributes, and the binding is emitted to `src/lib/bindings/AppSettings.generated.ts`. `storage.rs` delegates to the store, which persists `settings.json` and `ui-state.json`; a stored value is merged only if it round-trips through its field's serde type and a known key with a wrongly-typed value is rejected with `invalid-input`.

### Key Concepts
- **Typed Error Contract**: Every IPC command returns `Result<T, AppError>`. `AppError` serializes as `{code, message}` with kebab-case codes: `not-found`, `auth`, `remote`, `invalid-input`, `store`, `conflict`, `gone`, `not-ready`, `internal`. The frontend mirror lives in `src/lib/errors.ts` (`BackendErrorCode`). Never return raw strings from commands. `not-ready` means the app is still starting (the store/HTTP client is managed in `setup`, after the webviews exist): the frontend retries it briefly in `AppStore::bootstrap`, so anything that can legitimately run that early must not be reported with it.
- **Event Name Constants**: Backend event names are constants in `src-tauri/src/ipc_events.rs`, mirrored in `src/lib/ipcEvents.ts` (`stopwatch-updated`, `store-updated`, `deep-link`, `screen-effect`). Never inline raw event strings on either side.
- **Agent CLI**: `src-tauri/src/bin/taskroot.rs` (a second binary target) is a thin `main` over `src-tauri/src/cli/` (for agents and scripts), run as `bun run cli -- <verb>` or `cargo run --bin taskroot -- <verb>` from `src-tauri`. `cli/args.rs` parses the flags, `cli/session.rs` resolves `TASKROOT_DATA_DIR`/app-data and loads `account.json` + the keychain password, `cli/commands/` holds the verb bodies, `cli/help.rs` owns `VERBS`/`OPTIONS` and `docs/cli.md`, and `cli/output.rs` prints JSON/errors. It runs `ops::full_load` on **every** call before delegating to `store::ops` / `store::query` / `domain::projection::expand_event_instances`. It contains no ICS logic, so the merge invariants still hold. Output is JSON on stdout, `AppError` text on stderr with a non-zero exit; id arguments accept unique prefixes. Verbs: `lists`, `list-rm`, `tasks`, `task-show|add|set|done|rm`, `events`, `event-add|rm` (run `bun run cli -- help`). `list-rm` deletes a collection through the same `caldav::calendars::delete` the app uses; `task-set --list NAME` moves a task between lists. Every `<id>` verb accepts several ids in one invocation and prints a JSON array. The verb table (`VERBS`/`OPTIONS` in `cli/help.rs`) is the single source of truth for the help text and for `docs/cli.md`; a test regenerates that file on `cargo nextest run` and another fails if a dispatched verb is missing from the table, so neither can drift. It owns a private `Store`, so its writes reach a running app only when the user presses Refresh (or restarts the app). Unit tests in `cli/args.rs` and `cli/commands/` cover argument parsing, the flags→`AppTask` mapping and id-prefix/list resolution — the whole command surface that does not need a server.
- **Generated Bindings Flow**: `cargo nextest run` in `src-tauri` regenerates `src/lib/bindings/*.generated.ts` via `ts-rs` (`export_bindings_*` tests). After changing any `#[derive(TS)]` struct, run `cargo nextest run` and commit the regenerated files. CI fails on binding drift (`git diff --exit-code src/lib/bindings`) and on a stale `docs/cli.md`. The `#[ts(type = "number")]` convention keeps timestamps as JS `number` — never `bigint`.
- **Adding a Setting**: Declare the field on `AppSettings` with a `#[setting(label = ..., kind = ..., section = ..., ...)]` attribute (`src-tauri/src/settings/mod.rs`). `#[derive(SettingsMeta)]` turns those attributes into `get_settings_schema`'s output and derives each `defaultValue` from `AppSettings::default()`, so a setting is described once. A field without `#[setting(..)]` fails to compile; a new section is added to `SETTING_SECTIONS`. Field order sets the row order inside a section, and `SETTING_SECTIONS` order sets tab/section order. Run `cargo nextest run` to regenerate the `AppSettings` TS binding.
- **No Migrations**: Taskroot has a single user who keeps backups. Never add data-migration or legacy-compatibility code: no rewriting stored values into a new shape, no seeding from old `localStorage` keys, no fallback branches for removed settings. Change the current schema/default outright and let old files be reset or restored by hand.
- **Event Instance Projection**: Stored `AppEvent`s keep the canonical wall-clock/all-day strings the ICS writer consumes. The render path consumes `EventInstance`s produced by `domain::projection::expand` and returned by `query_event_instances`. All-day occurrences are floating dates (`startDate`/`endDateExclusive`) expanded independently of the process timezone; timed occurrences carry UTC instants. A timed row's wall-clock strings are interpreted in `AppEvent.timezone` and recurrence is expanded in that zone (`DTSTART;TZID=…`), so a weekly 09:00 event keeps 09:00 local across a DST change even though the instances are UTC. `AppEvent.exdates` (canonical `YYYY-MM-DD` / wall clock) is the single home of exclusion dates and is passed to the rule engine instead of being scanned out of `rrule`. `occurrenceKey` (`masterId@<date|rfc3339>`) is the stable per-occurrence identity and the key for exception/cancellation suppression; `occurrenceStart` carries the same occurrence's canonical `EXDATE`/`RECURRENCE-ID` value (bare date for all-day, wall clock in the event zone for timed). Occurrence identity is part of the write contract: `delete_event`/`reschedule_event` take an `EventScope` (`this`/`following`/`all`) plus that `occurrenceStart`, and the backend composes the `EXDATE`, `RECURRENCE-ID` exception or `UNTIL` truncation there. The frontend never builds `.ics` text. `query_events` still returns raw `AppEvent`s for the inspector.
- **Multi-Day Event Spanning**: `screens/plan/date-grid/spanLayout.ts` (`layoutWeekSpans`) clips each multi-day all-day instance to its week and packs the segments into non-overlapping lanes. `DateGrid` renders one spanning bar per week, with `date-grid/` keeping single-day all-day and timed events inline in the `DayCell`. The grid never duplicates a multi-day event into every day cell.
- **Multi-Window Architecture**: Five windows are declared in `tauri.conf.json`:
  - **Main Window** (`main`): The primary Svelte app; hides to tray on close.
  - **Launcher Window** (`launcher`): A spotlight-like command palette triggered via the global-shortcut plugin.
  - **Mini Tracker Window** (`minitracker`): A minimal window for tracking time. It runs independently but reads state from the Rust backend.
  - **Sidebar Window** (`sidebar`): A transparent, always-on-top companion pane anchored beside the main window.
  - **Effect Window** (`effect`): A hidden transparent, always-on-top, click-through fullscreen overlay that plays the phase-transition screen effect. `show_screen_effect`/`hide_screen_effect` drive it and the `SCREEN_EFFECT` event restarts its canvas animation.
  All of them render the same SPA, branched by window label in `+layout.svelte`.
- **Cross-Window State**: There is no dedicated inter-window wiring module. Window-specific state (stopwatch) lives in Rust and is shared across windows through Tauri commands (`get_stopwatch_state`, `toggle_stopwatch`, `toggle_break`, `toggle_pause`, `adjust_pause`, `reset_stopwatch`) plus backend-emitted events consumed via `listen` with the `src/lib/ipcEvents.ts` constants.

## Style (Important)
- **Generated Code**: Never hand-edit anything in `src/lib/bindings/` — regenerate via `cargo nextest run`.
- **Test-Driven Development**: Write tests first as a contract. Do not modify them unless there is something truly wrong.
- **Self-Documenting Code**: Avoid redundant comments. Extract complex logic into well-named functions or constants.
- **Small, Modular Code**: Refactor files if they exceed 250 LOC. Refactor functions with more than 4 levels of indentation.
- **Store Assets Offline**: Store assets offline.
- **Calendar Write Semantics**: Every edit is a read-modify-write on the fetched `.ics` body: merge the DTO into the stored raw resource (`ics::write_*_resource`), then `PUT` with `If-Match` (create: `If-None-Match: *`). Never serialize a DTO into a resource. A `412` re-fetches, re-merges and retries once; a second failure is reported to the UI. Deletes are `DELETE`; a repeating-event edit takes an `EventScope` and is resolved in `store::ops` — `this` writes an `EXDATE` or a `RECURRENCE-ID` exception, `following` truncates the rule before the occurrence, `all` touches the whole resource. See `docs/caldav.md`.
- Tautological tests are considered harmful.
- Please use early returns. This will make code nicer for you too.

## Development Environment Notes (Windows)

**The agent sandbox confines any executable stored inside this repository to writing inside the repository.** This is not an ACL or antivirus problem and it is not caused by the app:

- `src-tauri/target/debug/tauri-app.exe` gets `Access is denied (os error 5)` for `%APPDATA%`, `%LOCALAPPDATA%`, `%TEMP%`, `Desktop`, `Documents` and `C:\`; only paths under the repo succeed.
- The very same binary copied to `Desktop` or `Documents` writes everywhere, and a copy of `cmd.exe` placed in the repo is confined exactly like the Rust binary. It also persists when the exe is launched through Task Scheduler, so it is keyed on the image path, not on the parent process.
- The agent's shell is confined too, and so are things it spawns: under the `workspace-write` policy a write to `%APPDATA%`/`%TEMP%` fails even from a `C:\Windows\System32\cmd.exe` child, and the same write succeeds once the policy is `danger-full-access`. So a `Set-Content "$env:APPDATA\…"` that succeeds proves nothing about what the app can do, and one that fails does not prove the app is broken.

Consequences and the existing mitigations:

- `app_data_dir` (`src-tauri/src/lib.rs`) probes the platform app-data directory and, when a **debug build** cannot write it, uses `<exe dir>/dev-data` instead, seeding `account.json`, `settings.json` and `ui-state.json` from the real directory once and logging a warning. `TASKROOT_DATA_DIR` always wins. So `run.bat`/`bun run tauri dev` is usable for daily work with data in `src-tauri/target/debug/dev-data`; delete that directory to re-seed from `%APPDATA%\com.arkma.tauri-app`.
- **The linker needs `%TEMP%`.** `link.exe` creates `lnk{<guid>}.tmp` in `%TEMP%` and reopens it; a confined build cannot, and the compile dies at the final link with `LNK1104: cannot open file '…\Temp\lnk{…}.tmp'` even though every object compiled. `run.bat` pins `TMP`/`TEMP` at `src-tauri/target/cargo-tmp` for this reason; from a shell, set `$env:TMP`/`$env:TEMP` the same way before `cargo build`/`bun run tauri dev`. Measurements: the full link takes ~40 s with a writable `TMP`, ~24 s when `TMP` is the harness's own temp dir; the failing build died on the `%TEMP%` file while every object and dependency had compiled.
- The `App data directory … is not writable` / `WebView2 profile directory … is not writable` lines on startup are that fallback working as designed, not a fault: `%APPDATA%\com.arkma.tauri-app` and `%LOCALAPPDATA%\com.arkma.tauri-app` are normally writable (their ACLs are fine), the confined process simply cannot write them.
- Anything that must persist during a sandboxed run has to live under the repo. Rust tests already write under `src-tauri/target/…`; Vitest needs `TEMP`/`TMP` pointed at `src-tauri/target/vitest-tmp` for the same reason.
- Bulk edits: PowerShell `-replace` is case-insensitive and will silently rewrite identifiers (`caldav` → `CalDAV`). Prefer `edit`/`.Replace` or `-creplace`.
