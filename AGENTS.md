# Taskroot-rs Architecture & Guide for AI Agents

**CRITICAL**: When you modify the architecture, tech stack, or file structure of this project, you MUST update this `AGENTS.md` file to reflect the new state. Always verify if the information here is outdated and update any old information if needed.

*Note: Domain-specific rules are located in `src/AGENTS.md` (for Svelte) and `src-tauri/AGENTS.md` (for Rust).*

## Working With the User
- **Never screenshot the desktop or a running app to inspect the UI.** Do not launch the app just to capture it either. The user runs it themselves and will send a screenshot or describe the screen when asked — ask them.
- Prefer non-visual introspection for your own checks: ask the user, read logs, or reason from the code. Screen capture is for image files the user hands you, not for verification.

Taskroot is a desktop task management app focusing on planning, executing, and resting. It is built as a Svelte 5 application running on a native Tauri v2 Rust backend.

## Tech Stack
- **Package Manager**: Bun (`bun`). Used for package management and running frontend scripts.
- **Frontend Framework**: Svelte 5 with SvelteKit configured for SPA (Single Page Application) mode (`ssr = false` in `src/routes/+layout.ts`, `adapter-static` with an `index.html` fallback). Uses Svelte runes for reactivity.
- **Build Tool**: Vite (via SvelteKit), fixed dev port 1420 (`vite.config.js`).
- **Desktop Wrapper**: Tauri v2 (Rust backend, configured in `src-tauri/tauri.conf.json`).
- **Language**: TypeScript (`.ts`, `.svelte`) on the frontend, Rust (`.rs`) on the backend.
- **Styling**: Vanilla CSS (`src/app.css`) with extensive use of CSS variables for theming.
- **Backend / Storage**: One CalDAV server (local Radicale) is the source of truth. At startup the Rust backend loads every collection into an in-memory `Store` (`src-tauri/src/store/`) and writes a read-only `snapshot.json` cache; edits merge into the stored raw `.ics` and `PUT` immediately. App settings and per-component UI state live in `settings.json` / `ui-state.json`. There is no SQLite database, offline queue or Google client any more.
- **Type Sharing**: `ts-rs` generates `src/lib/bindings/*.generated.ts` from Rust structs; `cargo nextest run` is the regeneration trigger (see Key Concepts).
- **Testing**: 
  - **Frontend E2E**: Playwright (`playwright.config.ts`, specs in `tests/e2e/`, run via `bun run test`; the config boots `bun run dev` on port 1420 with chromium).
  - **Frontend Unit**: Vitest with jsdom (`bun run test:unit`). Coverage is collected via `@vitest/coverage-v8` (`bun run coverage:frontend`).
  - **Backend**: Rust unit tests (`cargo nextest run` in `src-tauri`, including CalDAV XML-parser fixtures, ICS round-trip invariants and `AppError` shape checks). `src-tauri/examples/e2e_caldav.rs` is the live Radicale check. Coverage is collected via `cargo-llvm-cov` (`bun run coverage:backend`, requires `cargo install cargo-llvm-cov`).
- **Linters**: ESLint (strictTypeChecked; `**/*.generated.ts` is exempt from `array-type` and `consistent-type-definitions` in `eslint.config.js`) and Rust `clippy` (`lib.rs` warns on pedantic/nursery and denies `unwrap`/`expect`). CI (`.github/workflows/ci.yml`) runs `bun run check` + `bun run lint` and `cargo clippy --all-targets -- -D warnings` + `cargo nextest run`. **CRITICAL: You must run `bun run check` (for frontend) and `cargo clippy` (for backend) after EVERY change to ensure code quality and avoid regressions.**

## Project Structure
- `src/`: SvelteKit frontend codebase.
  - `src/routes/`: SvelteKit routing (`+layout.svelte`, `+page.svelte`). The single SPA branches on the Tauri window label (`main`, `launcher`, `minitracker`, `sidebar`, `effect`) inside `+layout.svelte`. `src/routes/effect/` is the transparent, click-through full-screen phase-transition overlay.
  - `src/routes/settings/`: Settings screen split into `schema.ts` (typed schema consuming the generated `AppSettings` type) and `SettingRow.svelte`.
  - `src/lib/`: Shared logic and Svelte runes:
    - `store.svelte.ts`: Primary store. Mutations return `neverthrow` `Result`s, await the backend command, then re-fetch raw state from the Rust store. `init()` is idempotent (one cached bootstrap promise) and reads `get_settings` once on mount.
    - `safeInvoke.svelte.ts`: `safeInvoke` (`ResultAsync` wrapper over `invoke`) and the `useTauriQuery` rune (stale-guard via request IDs, optional `debounceMs`).
    - `errors.ts`: Typed `BackendErrorCode`/`AppError` glue mirroring the Rust `AppError` contract (`normalizeAppError`, `describeAppError`).
    - `events.ts`: TypeScript mirrors of the backend event-name constants in `src-tauri/src/events.rs`.
    - `eventColor.ts`: Shared event-accent presentation (`eventColorVars`) emitting the `--ev-color`/`--ev-bg` custom properties both the date grid and day timeline consume, so their colors cannot diverge.
    - `time.ts`: Local-date helpers (`ymd`, `addDays`, `dayDiff`, `sameDay`). Never use `toISOString()` for day bucketing (it shifts to UTC).
    - `useNow.svelte.ts`: Shared reactive `now` primitive (one interval, cleaned up automatically); use it instead of ad-hoc rAF loops.
    - `persisted.svelte.ts`: `persistState` rune + `persistedKeys` that hydrate per-component UI state (filters, sorts, view modes, pane sizes, collapsible sections) from `ui-state.json` via `get_ui_state` and debounce-save changes via `set_ui_state`, flushing pending writes on destroy.
    - `asyncState.svelte.ts`: Shared backend-hydration primitives composed by `persistState` and `useTauriQuery`: `createStaleGuard` (drop out-of-order responses), `createDebouncedWriter` (coalesce writes + flush on demand), and `hydrateOnce` (read-once-on-mount). Not a framework; compose them and keep state local.
    - `routes.ts`: Centralized route-path constants.
    - `domain.ts`: Centralized domain barrel re-exporting generated bindings from `src/lib/bindings/` and domain models/events/timing/filters (modularized in `src/lib/domain/models.ts`, `events.ts`, `timing.ts`, `filters.ts`). `timing.ts` provides the only render-path day-overlap helpers (`instanceOccursOnDay`, `isAllDayTiming`).
  - `src/lib/bindings/`: Generated TypeScript bindings (`.generated.ts`) for Rust data structures (generated via `ts-rs` by running `cargo nextest run` in `src-tauri`). Never hand-edit.
  - `src/screens/`: Major UI views. `plan/` (with `day-timeline/`, including `hooks/pointerGesture.svelte.ts` — a window-pointer gesture registry with `pointercancel` and teardown safety — and `date-grid/`, plus `hooks/eventDrag.svelte.ts`, `date-grid/dropPayload.ts`, and `date-grid/spanLayout.ts` for pointer drag-and-drop of grid instances onto other grid days or the timeline, with multi-day all-day events rendered as per-week spanning bars) and `do/` (with `stopwatch/`, whose `engine.svelte.ts` consumes the generated `StopwatchState`, defaults to the flowtime/flomodoro clock — work counts up, taking a break counts down one fifth of the work done, then waits for the user to restart work — and still offers the plain counter style; it includes the timed pause, plays the transition WAVs, and triggers the screen-effect overlay). `sidebar/state.svelte.ts` persists the sidebar's tab position/notes/visibility under `ui.sidebar.*` in `ui-state.json`.
  - `src/components/`: Reusable UI components. `ComingSoon.svelte` consolidates the seven stub route pages; `inspector-pane/` is split into `InspectorPane`, `InspectorTaskFields`/`InspectorEventFields`, and `format.ts`.
  - `src/test/`: Shared test utilities (`tauriMock.ts`, the process-wide Tauri IPC mock used by component tests). See `src/AGENTS.md` for the testing conventions.
- `src-tauri/`: Tauri Rust backend.
  - `src-tauri/src/lib.rs`: Lints, module wiring, app-data resolution (`app_data_dir`: `TASKROOT_DATA_DIR` override, plus a debug-build fallback to `<exe dir>/dev-data` when the real app-data directory is not writable — see Development Environment Notes), managed `StoreState`, startup load and `run()`. IPC commands live in `commands/`, not here.
  - `src-tauri/src/commands/`: IPC command handlers split by domain (`tasks.rs`, `events.rs`, `window.rs`, `sync.rs`) plus `session.rs` (shared `client_for`/`store_state`/`app_calendar` plumbing). Every handler is a thin wrapper over the store/CalDAV layer; `commands/tests.rs` pins the `generate_handler!` table against the frontend call sites (see `src-tauri/AGENTS.md` → Command Testing).
  - `src-tauri/src/caldav/`: CalDAV protocol layer. `transport.rs` owns the shared `reqwest::Client` and status mapping; `xml.rs` holds request bodies and `roxmltree` parsers; `discovery.rs` resolves principal → calendar-home → collections; `account.rs` persists `account.json` and the keychain password; `client.rs` adds `fetch_resources`/`fetch_hrefs`/`sync_collection`/`put_resource`/`delete_resource`/`mkcalendar`; `commands.rs` exposes the account commands; `model.rs` defines `CalendarInfo`/`CalendarComponent`.
  - `src-tauri/src/store/`: The CalDAV-backed in-memory store. `model.rs` holds `Store`/`Resource`/`Snapshot`; `ops.rs` does `full_load`/`pull` and create/update/delete (immediate `PUT`/`DELETE`, one re-fetch/retry on `412`); `query.rs` is the in-memory filter/sort/search; `persist.rs` reads/writes `settings.json` and `ui-state.json`; `state.rs` is the managed `tokio::sync::Mutex` handle. `snapshot.json` is only a cache for an unreachable server.
  - `src-tauri/src/error.rs`: `AppError` enum (`thiserror`) returned by ALL IPC commands; serialized as `{code, message}`.
  - `src-tauri/src/events.rs`: Centralized event-name constants (`STOPWATCH_UPDATED`, `SYNC_STARTED/FINISHED/ERROR`, `DEEP_LINK`, `SCREEN_EFFECT`).
  - `src-tauri/src/domain/`: Core data structures (`mod.rs`, `sigil.rs` for sigil parsing, `filters.rs` for filter columns/types) plus `event_timing.rs` — the **single normalization boundary** (`EventTiming`, `EventInstance`, `EventTiming::from_event`) that turns raw calendar strings into tagged all-day/timed timing. Nothing outside this module may parse `AppEvent::start_time`/`end_time`.
  - `src-tauri/src/ics/`: CalDAV resource ↔ DTO conversion (`caldav-migration-plan.md` §7–§9). `read.rs` maps a whole `.ics` body (with `icalendar`) to `Vec<AppEvent>`/`Vec<AppTask>`; `write.rs` is the line-preserving editor that merges an edit into the fetched bytes (only Taskroot-owned property lines change; `VTIMEZONE`, `VALARM`, `ATTENDEE`, unknown `X-*` survive verbatim) and `lines.rs` holds that editor's folding/component-spanning core. `create_*_resource` builds a brand-new resource with `icalendar`'s builder. Never serialize a DTO to a resource (I1), a resource is a set of components sharing a UID (I2), and unknown components never round-trip through `icalendar` (I3). Fixtures under `ics/fixtures/` are real Radicale resources.
  - `src-tauri/src/sync/`: Sync engine: `mod.rs` (5-minute poller honouring `sync_interval`, `SyncState` with `offline`/`last_synced`, debounced `SyncTrigger`, `sync_all`), which pulls per-collection `sync-collection` deltas into the store and falls back to `snapshot.json` when the server is unreachable. There is no push queue: edits `PUT` immediately.
  - `src-tauri/src/stopwatch.rs`: Stopwatch backend (`StopwatchState` struct plus `get/toggle_break/toggle_pause/adjust_pause/reset_stopwatch` commands).
  - `src-tauri/src/settings/`: Settings backend, split into `mod.rs` (`AppSettings` struct with `#[derive(TS)]` and `#[derive(SettingsMeta)]` field-adjacent metadata plus the IPC commands) and `metadata.rs` (`SettingMeta`/`SettingOption`, `SETTING_SECTIONS`, `CUSTOM_SETTINGS`, and `build_settings_schema`, with tests in `metadata/tests.rs`). `get_settings_schema` is generated from the field attributes, and the binding is emitted to `src/lib/bindings/AppSettings.generated.ts`. `storage.rs` delegates to the store, which persists `settings.json` and `ui-state.json`; a stored value is merged only if it round-trips through its field's serde type and a known key with a wrongly-typed value is rejected with `invalid-input`.

### Key Concepts
- **Typed Error Contract**: Every IPC command returns `Result<T, AppError>`. `AppError` serializes as `{code, message}` with kebab-case codes: `not-found`, `auth`, `sync`, `invalid-input`, `store`, `conflict`, `gone`, `not-ready`, `internal`. The frontend mirror lives in `src/lib/errors.ts` (`BackendErrorCode`). Never return raw strings from commands. `not-ready` means the app is still starting (the store/HTTP client is managed in `setup`, after the webviews exist): the frontend retries it briefly in `AppStore::bootstrap`, so anything that can legitimately run that early must not be reported with it.
- **Event Name Constants**: Backend event names are constants in `src-tauri/src/events.rs`, mirrored in `src/lib/events.ts` (`stopwatch-updated`, `sync-started`, `sync-finished`, `sync-error`, `screen-effect`). Never inline raw event strings on either side.
- **Generated Bindings Flow**: `cargo nextest run` in `src-tauri` regenerates `src/lib/bindings/*.generated.ts` via `ts-rs` (`export_bindings_*` tests). After changing any `#[derive(TS)]` struct, run `cargo nextest run` and commit the regenerated files. CI fails on binding drift (`git diff --exit-code src/lib/bindings`). The `#[ts(type = "number")]` convention keeps timestamps as JS `number` — never `bigint`.
- **Adding a Setting**: Declare the field on `AppSettings` with a `#[setting(label = ..., kind = ..., section = ..., ...)]` attribute (`src-tauri/src/settings/mod.rs`). `#[derive(SettingsMeta)]` turns those attributes into `get_settings_schema`'s output and derives each `defaultValue` from `AppSettings::default()`, so a setting is described once. A field without `#[setting(..)]` fails to compile; a new section is added to `SETTING_SECTIONS`. Field order sets the row order inside a section, and `SETTING_SECTIONS` order sets tab/section order. Run `cargo nextest run` to regenerate the `AppSettings` TS binding.
- **No Migrations**: Taskroot has a single user who keeps backups. Never add data-migration or legacy-compatibility code: no rewriting stored values into a new shape, no seeding from old `localStorage` keys, no fallback branches for removed settings. Change the current schema/default outright and let old files be reset or restored by hand.
- **Event Instance Projection**: Stored `AppEvent`s keep the canonical wall-clock/all-day strings the ICS writer consumes. The render path consumes `EventInstance`s produced by `screens::plan::expand` and returned by `query_event_instances`. All-day occurrences are floating dates (`startDate`/`endDateExclusive`) expanded independently of the process timezone; timed occurrences carry UTC instants. A timed row's wall-clock strings are interpreted in `AppEvent.timezone` and recurrence is expanded in that zone (`DTSTART;TZID=…`), so a weekly 09:00 event keeps 09:00 local across a DST change even though the instances are UTC. `AppEvent.exdates` (canonical `YYYY-MM-DD` / wall clock) is the single home of exclusion dates and is passed to the rule engine instead of being scanned out of `rrule`. `occurrenceKey` (`masterId@<date|rfc3339>`) is the stable per-occurrence identity and the key for exception/cancellation suppression. `query_events` still returns raw `AppEvent`s for the inspector; drag/resize calls `reschedule_event`.
- **Multi-Day Event Spanning**: `screens/plan/date-grid/spanLayout.ts` (`layoutWeekSpans`) clips each multi-day all-day instance to its week and packs the segments into non-overlapping lanes. `DateGrid` renders one spanning bar per week, with `date-grid/` keeping single-day all-day and timed events inline in the `DayCell`. The grid never duplicates a multi-day event into every day cell.
- **Multi-Window Architecture**: Five windows are declared in `tauri.conf.json`:
  - **Main Window** (`main`): The primary Svelte app; hides to tray on close.
  - **Launcher Window** (`launcher`): A spotlight-like command palette triggered via the global-shortcut plugin.
  - **Mini Tracker Window** (`minitracker`): A minimal window for tracking time. It runs independently but reads state from the Rust backend.
  - **Sidebar Window** (`sidebar`): A transparent, always-on-top companion pane anchored beside the main window.
  - **Effect Window** (`effect`): A hidden transparent, always-on-top, click-through fullscreen overlay that plays the phase-transition screen effect. `show_screen_effect`/`hide_screen_effect` drive it and the `SCREEN_EFFECT` event restarts its canvas animation.
  All of them render the same SPA, branched by window label in `+layout.svelte`.
- **Cross-Window State**: There is no dedicated inter-window wiring module. Window-specific state (stopwatch, sync status) lives in Rust and is synced across windows through Tauri commands (`get_stopwatch_state`, `toggle_stopwatch`, `toggle_break`, `toggle_pause`, `adjust_pause`, `reset_stopwatch`, `get_sync_state`) plus backend-emitted events consumed via `listen` with the `src/lib/events.ts` constants.

## Style (Important)
- **Generated Code**: Never hand-edit anything in `src/lib/bindings/` — regenerate via `cargo nextest run`.
- **Test-Driven Development**: Write tests first as a contract. Do not modify them unless there is something truly wrong.
- **Self-Documenting Code**: Avoid redundant comments. Extract complex logic into well-named functions or constants.
- **Small, Modular Code**: Refactor files if they exceed 250 LOC. Refactor functions with more than 4 levels of indentation.
- **Store Assets Offline**: Store assets offline.
- **Calendar Write Semantics**: Every edit is a read-modify-write on the fetched `.ics` body: merge the DTO into the stored raw resource (`ics::write_*_resource`), then `PUT` with `If-Match` (create: `If-None-Match: *`). Never serialize a DTO into a resource. A `412` re-fetches, re-merges and retries once; a second failure is reported to the UI. Deletes are `DELETE`; a repeating-event exception removes only its component. See `docs/caldav.md`.
- Tautological tests are considered harmful.
- Please use early returns. This will make code nicer for you too.

## Development Environment Notes (Windows)

**The agent sandbox confines any executable stored inside this repository to writing inside the repository.** This is not an ACL or antivirus problem and it is not caused by the app:

- `src-tauri/target/debug/tauri-app.exe` gets `Access is denied (os error 5)` for `%APPDATA%`, `%LOCALAPPDATA%`, `%TEMP%`, `Desktop`, `Documents` and `C:\`; only paths under the repo succeed.
- The very same binary copied to `Desktop` or `Documents` writes everywhere, and a copy of `cmd.exe` placed in the repo is confined exactly like the Rust binary. It also persists when the exe is launched through Task Scheduler, so it is keyed on the image path, not on the parent process.
- The agent's own shell is *not* confined, so `Set-Content "$env:APPDATA\…"` succeeding proves nothing about what the app can do.

Consequences and the existing mitigations:

- `app_data_dir` (`src-tauri/src/lib.rs`) probes the platform app-data directory and, when a **debug build** cannot write it, uses `<exe dir>/dev-data` instead, seeding `account.json`, `settings.json` and `ui-state.json` from the real directory once and logging a warning. `TASKROOT_DATA_DIR` always wins. So `run.bat`/`bun run tauri dev` is usable for daily work with data in `src-tauri/target/debug/dev-data`; delete that directory to re-seed from `%APPDATA%\com.arkma.tauri-app`.
- Anything that must persist during a sandboxed run has to live under the repo. Rust tests already write under `src-tauri/target/…`; Vitest needs `TEMP`/`TMP` pointed at `src-tauri/target/vitest-tmp` for the same reason.
- `snapshot.json` is only the offline cache, so its write failures are logged and ignored (`Store::write_snapshot`) rather than failing the load or an edit. `settings.json` / `account.json` writes still fail loudly — that is deliberate.
- Bulk edits: PowerShell `-replace` is case-insensitive and will silently rewrite identifiers (`caldav` → `CalDAV`). Prefer `edit`/`.Replace` or `-creplace`.
